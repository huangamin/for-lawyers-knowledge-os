# 学引力 Knowledge OS 搭建规范（V1.8）

> 本规范是知识库的**唯一分类基准（source of truth）**：明确每个库负责什么、内容该放哪里。所有摄入 / 归档 / 查询必须先读本规范，再确定归属。
>
> 依据：ChatGPT 手册《学引力 Learning OS》（https://chatgpt.com/s/t_6a7e84961e408191a857c344d1579e3c）中的板块分类设计。
>
> **核心原则（唯一）——共同进化**：学习驱动知识库，知识库反哺学习。每次学习、教学、研究的产出都必须进库；Query、Lint、概念缺口必须能告诉你下一步该学什么。本规范所有规则都服务于"让知识库与学习共同进化"。

## 0. 用途与执行方式

- 目录骨架已按本规范**物理建立**（68 个分类子目录），后续内容按此归位。
- 每次 Store / Ingest 先判断内容类型 → 查"摄入路由规则"（第 6 节）→ 写入对应库/子目录。
- 原始素材一律进 `_Skill工作区/raw/`（只读）；整理后的页面进用户板块。

## 1. 总体原则

1. **十个一级目录固定，不增不减**；复杂的东西放在二三级。
2. **双向链接是核心**：新页面必须至少关联 1 个已有页面；文件夹只是容器，Link 才是知识库。
3. **知识成熟度三分类**：`[Evidence]` 已有较强研究证据 / `[Hypothesis]` 学引力假设 / `[Practice]` 真实教学观察。
4. **Learning OS 知识进阶**：`#observation` → `#hypothesis` → `#testing` → `#evidence` → `#protocol`。
5. **数据边界**：Obsidian 存知识和规则，交易数据（收入/考勤/工资）放数据库。
6. **学生隐私**：一律用 STU-### / 化名。
7. **外部研究不能成为收藏夹坟墓**：必须回答"对学引力意味着什么"并链到具体页面。
8. **先 Inbox 再分类**：拿不准放哪的，先放 00 Inbox，定期按 Capture → Clarify → Distill → Connect → Apply 处理。
9. **原始文件固定上传**：用户提供 PDF / DOCX / 其他原始文件时，一律上传到 `_Skill工作区/raw/<主题>/`（只读层）并在整理页中链接，不留孤件。
10. **根目录结构固定**：根目录只保留 10 个板块文件夹 + `_Skill工作区`（功能文件夹）+ `CLAUDE.md` + `知识库总控台.md`（根目录唯一允许的附加文件），**不得再增加其他散落文件**；页面、附件、模板一律放入对应文件夹内。
11. **功能文件夹允许新增**：为收纳系统/工具类内容，可按需新增带下划线前缀的功能文件夹（如 `_Skill工作区`），避免目录混乱；板块根目录只放该板块的 MOC/文件夹笔记，不散放正文。
12. **Agent 设计原则（固定）**：先宪法后 SOP——CLAUDE.md / 总规则只定原则与边界（高位阶），各 Agent 专属 SKILL.md 承载具体流程（低位阶）；规则分层、不堆步骤；高位阶只定原则、低位阶承载细节。Learning OS 架构评审时直接引用本条。

## 4. 命名与模板

- 页面文件名：简洁、可读、避免特殊字符；同一实体保持稳定命名。
- 学生档案：`STU-###`（绝不写完整身份信息）。
- 重大决策：`Decision-YYYY-NNN`（含问题/决策/原因/被否决方案/验证条件/复盘日期）。
- 干预记录：含 Observation / Diagnosis / Intervention / Result / Retention / 关联链接。
- 模板位于 `_Skill工作区/_templates/`：source / concept / entity / synthesis / comparison。

## 5. 知识成熟度机制

所有 Learning OS 相关知识标注状态：

`🌱 Observation`（真实观察）→ `💡 Hypothesis`（形成假设）→ `🧪 Testing`（正在验证）→ `📊 Evidence`（数据支持）→ `⚙️ Protocol`（标准规则）

标签写法：`#observation` / `#hypothesis` / `#testing` / `#evidence` / `#protocol`；frontmatter 用 `maturity:` 字段。

**maturity 闸门（固定）**：

- AI 写入的新页面默认最高标 `💡 #hypothesis`，不得自行标 `#evidence` / `#protocol`；
- 升到 `📊 #evidence`：需用户确认 + 页面注明来源；
- 升到 `⚙️ #protocol`：需真实教学/实践记录（Observation / 数据）支撑。

## 7. 编译 / 回写 / 体检 / MOC 规范

### 7.1 Ingest 编译（矛盾检测 + 链式更新）

Ingest 不是"抄新页"，是"改旧稿"：

1. **矛盾检测**：新素材进来，先扫描 2–5 个最相关旧页面；发现冲突时，在新页面 frontmatter 标 `conflict: [[旧页]]` 并简述冲突点，判断留给用户，AI 不替用户拍板。
2. **链式更新**：新证据涉及旧页时，对受影响旧页做最小修正（更新过时结论、补充新证据、加反链），并把修改记录写进 `_Skill工作区/wiki/log.md`。

### 7.2 Query 回写

Query 不只是回答：值得沉淀的答案（新综合、新对比、可复用结论）经用户确认后，写入 `_Skill工作区/wiki/synthesis/`（或用户指定板块），并更新 index.md / log.md。知识库越用越厚，这就是"复利"。

### 7.3 Lint 内容三查

Lint 除结构检查（孤立页面、未标记成熟度、缺链接、缺索引、raw 污染）外，必须做三查：

- **跨页矛盾**：两页对同一概念/方法的说法是否冲突；
- **过期结论**：旧页结论是否已被新证据推翻（新证据 vs 旧说法）；
- **概念缺口**：同一概念在 ≥3 处出现却无独立页面 → 建议新建概念页。

报告问题清单，不擅自改动；用户确认后才修。

### 7.4 MOC 规范

- 每个板块根目录必须有且只有 1 个 MOC/文件夹笔记（命名与板块同名，如 `02 LearningOS｜最核心板块.md`），列明使命、子目录、现有内容、相关链接。
- 板块正文一律放子目录，不放板块根目录。
- 每轮 Store / Ingest / Archive 后，若板块内容变化，同步更新对应板块 MOC。

### 7.5 Update-in-place（版本规则）

- 同一概念只准有一个页面：同标题合并更新，禁建 `xxx v2` / `xxx 副本` / `xxx 终版` 等版本化标题。
- 版本演变记在 `_Skill工作区/wiki/log.md`，不活在标题里。
- 例外：
  - `raw/` 只读层：原始文件永不改名/合并（如 `2026-08-14-公司战略蓝图V1.0.md` 保留原名）。
  - 按编号/日期自然分实体的记录：Decision Log、学生档案、干预记录、实验记录、产品迭代实体（如 Learning OS 0.1）——每个编号是新实体，不是页面版本。
- 合并改名时，旧标题写入新页面 frontmatter `aliases:`，保持旧链接可用。

## 9. 规则治理（全局底层逻辑 · Codex 与知识库建设必遵）

> 来源：《自进化系统全局规范》（raw/系统治理/2026-08-15-自进化系统全局规范.md），2026-08-15 定为全局底层逻辑。本规范自身属于 L1 法律层，受 L0 宪法层约束。

### 9.1 核心元原则

- 系统进化 ≠ 知识增加；系统进化 = 有效经验被抽象为规则 → 规则被验证 → 旧规则被淘汰 → 整体复杂度下降、执行能力提高。
- 最高目标：**Maximum Generalization + Minimum Complexity**（最大化解释力、最小化系统复杂度）。
- 每次执行后用两个变量评估：**Execution Gain**（成功率/错误/效率/自主决策）与 **Complexity Cost**（规则数量/冲突/例外/检索范围/维护成本/决策路径长度）。进化 = 最大化 Execution Gain / Complexity Cost。
- 默认流程："积累 → 抽象 → 合并 → 修正 → 废止 → 再评估"，不是"遇到问题 → 加一条规则"。

### 9.2 规则位阶（法秩序类比）

| 层级 | 名称 | 载体 | 说明 |
|---|---|---|---|
| L0 | 宪法层 | `CLAUDE.md`（根目录） | 极少量跨任务长期有效的根原则；普通 Agent/Skill/SOP/案例不得直接修改，修改需用户（宪法制定者）确认 |
| L1 | 法律层 | 本规范（知识库搭建规范） | 跨任务稳定适用的系统政策：事实验证、写入规则、冲突处理、规则升级与废止 |
| L2 | 领域规则层 | 各板块规则/路由 | 按领域建立（Education / Research / Operations 等），不得违反上位规则 |
| L3 | SOP 层 | Skill / 操作流程 | 把上位原则转为具体执行流程；应尽可能简洁，变长时检查是否应上升为更高层规则 |
| L4 | 案例层 | 05 Students 案例库 / 执行记录 | Task/Context/Decision/Tool Calls/Result/Failure/Feedback/Outcome；**Case ≠ Rule** |
| L5 | 证据层 | `_Skill工作区/raw/` | 文档、官方资料、执行日志、数据；证据是规则依据，但本身不等于规则 |

### 9.3 案例 → 规则演化流程（禁止把案例直接变规则）

Case → Observation → Pattern → Candidate Rule → Conflict Check → Complexity Check → Validation → Rule Promotion

- 单次案例 = 观察；
- 重复模式 = 候选规则；
- 稳定规律 = 正式规则。

### 9.4 压缩优先（新增规则前按序检查）

1. 已有规则能否解释？→ 能则不新增；
2. 存在重复规则？→ Merge；
3. 存在冲突规则？→ Amend / Replace；
4. 能否通过修改上位规则解决？→ 改上位，不增下位；
5. 只是一次性特殊情况？→ 保留为 Case，不进规则体系；
6. 新规则是否显著提升执行结果？→ 不能则拒绝新增。

### 9.5 规则废止制度

所有非宪法规则必须允许状态：ACTIVE → AMENDED / MERGED / DEPRECATED / RETIRED。规则不能因"曾经有用"而永久存在。元数据模板：

```yaml
rule_id:
level:
domain:
status:
created_at:
last_validated_at:
usage_count:
success_rate:
conflict_count:
exception_count:
complexity_cost:
replacement_candidate:
review_after:
```

**账本最小实装（V1.8 起，审计修复）**：
- `review_after` 挂在规则载体页面自身的 frontmatter（本规范、CLAUDE.md、说明书等治理页已补），Lint 四查负责到期扫描；
- `usage_count` / `success_rate` / `conflict_count` 等统计字段在规则数较少阶段允许留空或标"未采集"，采集时机为 Lint 时人工确认一次；
- 规则数超过约十几条、或出现"一页承载多规则且需独立统计"时，升级为独立注册表（遵循"单次案例不升级"，不提前建）；
- 每次规则变动后，除本规范修订记录外，必须同步《Codex 进化治理与法学类比说明书》第四节变动记录（该义务已并入 CLAUDE.md Operations 收尾步骤与 Lint 四查）。

## 10. 知识元数据规范（统一 Properties）

所有页面 frontmatter 遵循统一字段，在既有字段上扩展，不另建平行体系：

| 字段 | 必填 | 说明 | 枚举/示例 |
|---|---|---|---|
| `type` | ✔ | 页面类型 | moc / source / synthesis / concept / entity / decision / protocol / sop / demo / methodology / report / dashboard |
| `domain` | ✔ | 一级领域（对应板块） | Inbox / Strategy / LearningOS / LearningScience / Curriculum / Students / Coaching / Operations / Growth / Research / Governance |
| `subdomain` | 选填 | 二级子领域 | LearningProtocol / StudentModel / Companies / CoachSOP 等 |
| `layer` | 治理页必填 | 规则位阶（见第 9 节） | L0 宪法 / L1 法律 / L2 领域 / L3 SOP / L4 案例 / L5 证据 |
| `maturity` | 知识页必填 | 成熟度 | 🌱 Observation → 💡 Hypothesis → 🧪 Testing → 📊 Evidence → ⚙️ Protocol |
| `status` | ✔ | 生命周期 | active / ingested / archived |
| `origin` | ✔ | 来源性质 | 内部原创 / 外部摄入 / 学引力发展 / 用户决策 |
| `source` | 选填 | 原始资料 | raw 文件 wikilink 或 URL（对接 source_type / source_files / source_url） |
| `parent` | 选填 | 上级页面 | MOC 或父级页面 |
| `related_os` | 选填 | 关联 Learning OS 组件 | KnowledgeGraph / ErrorGraph / StudentModel / InterventionLibrary / LearningProtocol / Metrics / AIAgents |
| `confidence` | 选填 | 置信度 | high / medium / low |
| `created` / `updated` | created 必填 | 时间 | YYYY-MM-DD（created 对齐既有 date） |

**执行规则**：

1. 新页面按 `_templates` 模板创建，默认携带完整字段；
2. 存量页面**下次编辑时**补齐 `domain` + `origin`，不批量返工；
3. 总控台（`_Skill工作区/知识库总控台.md`）按此字段扫描呈现知识库状态；
4. 字段取值不确定时标 `confidence: low`，不得编造。

**附件链接规则（固定）**：指向 PDF / DOCX / 图片等附件的 wikilink 必须**带扩展名**（如 `[[xxx.pdf]]`），禁止使用不带扩展名的 `[[xxx]]` 链接附件——否则 Obsidian 会把它当作不存在的笔记，点击时可能触发"新建笔记"并产生根目录 0 字节空壳（2026-08-15 已发生 3 次）。
